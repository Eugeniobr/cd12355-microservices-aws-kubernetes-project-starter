\begin{tcolorbox}[colback=codebg,colframe=awsnavy,title=\textbf{Prefácio: O que este guia resolve?},fonttitle=\bfseries]
Se você vem da área de \textbf{Análise de Dados}, seu dia a dia geralmente envolve consultas SQL, manipulação de DataFrames com Pandas, criação de modelos e geração de relatórios. No entanto, quando essa análise precisa ser disponibilizada para centenas de pessoas como uma API rápida e estável, entramos no mundo de \textbf{DevOps e Engenharia de Nuvem}.

Este documento conta, passo a passo e sem jargões desnecessários, como pegamos uma aplicação em Python que consulta um banco PostgreSQL e a transformamos em uma solução profissional, resiliente e 100\% automatizada na \textbf{Amazon Web Services (AWS)} utilizando \textbf{Docker}, \textbf{Kubernetes (EKS)} e \textbf{Pipelines de CI/CD}.
\end{tcolorbox}

\section{O Mapa Mental dos Conceitos (Analogias do Mundo Real)}

Antes de mergulhar nos comandos, vamos traduzir os termos técnicos de DevOps para conceitos intuitivos:

\begin{itemize}[leftmargin=*]
    \item \textbf{Docker (O Contêiner):} Imagine que você criou um script Python no Jupyter Notebook com bibliotecas específicas e precisa mandar para um colega. Se o colega tiver outra versão do Python ou do Windows, tudo quebra. O Docker é uma ``marmita lacrada'' (contêiner) que carrega o seu código, a versão exata do Python, as bibliotecas do \texttt{requirements.txt} e até o sistema operacional mínimo. Onde essa marmita for aberta (no seu notebook, no servidor do chefe ou na nuvem), o script roda exatamente da mesma forma.
    
    \item \textbf{AWS ECR (O Armazém de Imagens):} É como um repositório seguro no Google Drive ou GitHub, mas específico para guardar essas ``marmitas lacradas'' (imagens Docker) prontas para serem usadas.
    
    \item \textbf{AWS CodeBuild (A Linha de Montagem / CI):} Em vez de você ficar compilando a imagem no seu computador toda vez que mudar uma linha de código, o CodeBuild é um computador descartável na nuvem que baixa seu código do GitHub, prepara a imagem Docker e a coloca no armazém (ECR) automaticamente.
    
    \item \textbf{Kubernetes (O Maestro da Orquestra):} Se sua marmita (contêiner) travar de madrugada ou se o servidor queimar, quem acorda para reiniciar? O Kubernetes. Ele monitora a saúde das aplicações, divide o trabalho entre computadores e garante que, se um processo morrer, outro seja criado em questão de segundos sem ninguém perceber.
    
    \item \textbf{AWS EKS (A Infraestrutura do Maestro):} É o serviço da AWS que monta toda a sala de máquinas do Kubernetes para você com segurança e alta disponibilidade.
    
    \item \textbf{Helm (O Instalador de Pacotes do Kubernetes):} Pense no Helm como o \texttt{pip} do Python ou o \texttt{apt} do Linux, só que para infraestrutura. Em vez de escrever 300 linhas de configuração para subir um banco PostgreSQL, você roda um único comando do Helm e o banco sobe completo.
\end{itemize}

\section{A Crônica Detalhada das Etapas (O Que Fizemos e Por Quê)}

A seguir, veja a narrativa real e sem cortes de cada passo percorrido, com as motivações por trás de cada comando:

\subsection{Etapa 1: O Ponto de Partida e o Mistério da AWS sem Chaves}
\textbf{O que aconteceu:} Ao tentar rodar \texttt{aws sts get-caller-identity} no terminal local, recebemos o erro informando que o comando não existia. Depois de instalá-lo, surgiu o erro \textit{``Unable to locate credentials''}.\\
\textbf{A explicação didática:} O utilitário \textbf{AWS CLI} é apenas o ``telefone'' que você usa para falar com os servidores da Amazon. Mas antes de a Amazon atender suas ordens, ela precisa saber quem está ligando. As variáveis de ambiente (\texttt{AWS\_ACCESS\_KEY\_ID}, \texttt{AWS\_SECRET\_ACCESS\_KEY} e \texttt{AWS\_SESSION\_TOKEN}) são como o seu crachá e senha temporária de acesso ao prédio da AWS. Uma vez exportadas no terminal, a AWS nos reconheceu imediatamente.

\subsection{Etapa 2: Erguendo a Cidade do Kubernetes com \texttt{eksctl}}
\textbf{O que aconteceu:} Executamos o comando:
\begin{lstlisting}
eksctl create cluster --name my-cluster --region us-east-1 --nodegroup-name my-nodes --node-type t3.small --nodes 1
\end{lstlisting}
O comando levou cerca de 18 minutos rodando silenciosamente no terminal.\\
\textbf{A explicação didática:} Uma dúvida natural foi: \textit{``esse comando fica rodando para sempre?''}. Não! Ele demorou porque o \texttt{eksctl} não instalou um simples programa; ele desenhou e ergueu uma infraestrutura inteira do zero na nuvem da AWS via CloudFormation:
\begin{enumerate}
    \item Criou uma \textbf{VPC} (uma rede privada isolada no datacenter da AWS em Virgínia do Norte).
    \item Criou sub-redes públicas e privadas com tabelas de roteamento e regras de firewall.
    \item Provisionou o \textbf{Control Plane} do Kubernetes (os servidores mestres que tomam decisões).
    \item Criou uma máquina virtual EC2 (\texttt{t3.small}) como nó operário (\textit{worker node}).
\end{enumerate}
Ao final, o \texttt{eksctl} salvou o arquivo \texttt{\textasciitilde/.kube/config}, que funciona como a chave mestra para que o comando \textbf{\texttt{kubectl}} possa controlar o cluster do nosso terminal.

\subsection{Etapa 3: Criando e Populando o Banco de Dados com Helm}
\textbf{O que aconteceu:} Subimos um PostgreSQL com o comando \texttt{helm install postgresql bitnami/postgresql} e em seguida populamos as tabelas com os scripts \texttt{1\_create\_tables.sql}, \texttt{2\_seed\_users.sql} e \texttt{3\_seed\_tokens.sql}.\\
\textbf{A explicação didática:} Para um analista, banco de dados é a alma do projeto. Em vez de criarmos manualmente máquinas para o banco, o \textbf{Helm} aplicou uma receita pronta da Bitnami. O banco gerou uma senha aleatória que ficou guardada em um objeto seguro do Kubernetes chamado \textbf{Secret}.\\
\textit{O obstáculo do caminho:} Quando tentamos conectar na porta \texttt{5432} via \textit{port-forward}, a senha falhava porque a máquina local já tinha outro PostgreSQL instalado ocupando a porta \texttt{5432}. Resolvemos isso de forma elegante: injetamos os arquivos SQL diretamente para dentro do contêiner do banco usando o comando \texttt{kubectl exec}, sem sofrer interferência da rede local.

\subsection{Etapa 4: Empacotando o Python no Docker e o Bug Oculto do Flask}
\textbf{O que aconteceu:} Criamos o \texttt{Dockerfile} baseado em \texttt{python:3.10-slim} e o enviamos para o cluster. Mas ao analisar os logs do pod com \texttt{kubectl logs}, nos deparamos com:
\begin{lstlisting}
ImportError: cannot import name 'url_quote' from 'werkzeug.urls'
\end{lstlisting}
\textbf{A explicação didática:} Este é um problema clássico de projetos de dados: o arquivo \texttt{requirements.txt} original dizia apenas \texttt{flask==2.2.2}. Como a biblioteca auxiliar \texttt{Werkzeug} não tinha versão travada, o pip baixou a versão mais nova (\texttt{Werkzeug 3.0}), que apagou uma função antiga que o Flask esperava. Corrigimos adicionando \texttt{Werkzeug==2.2.2}, garantindo reprodutibilidade matemática das dependências.

\subsection{Etapa 5: Automatizando a Nuvem com GitHub e AWS CodeBuild}
\textbf{O que aconteceu:} Configuramos o arquivo \texttt{buildspec.yml} e conectamos nosso repositório GitHub ao serviço \textbf{AWS CodeBuild}.\\
\textbf{A explicação didática:} O CodeBuild atua como um assistente de fábrica. Toda vez que iniciamos a compilação, ele aciona uma máquina virtual na AWS, lê as instruções do \texttt{buildspec.yml}, constrói a imagem Docker, adiciona as etiquetas de versão (\texttt{1.0.0} e \texttt{latest}) e publica a imagem no \textbf{AWS ECR}. A partir desse momento, qualquer servidor do nosso cluster tem acesso direto à imagem oficial da aplicação.

\subsection{Etapa 6: O Mistério do Pod que Não Ficava Pronto (Readiness Probe)}
\textbf{O que aconteceu:} Após o build, o comando \texttt{kubectl rollout status} ficou travado com a mensagem: \textit{``1 old replicas are pending termination...''}, e o pod novo aparecia como \texttt{0/1 Running}.\\
\textbf{A explicação didática:} No Kubernetes, um pod não recebe clientes só porque começou a rodar. O Kubernetes possui ``sensores médicos'' chamados \textbf{Probes}:
\begin{itemize}
    \item \textbf{Liveness Probe:} Pergunta se a aplicação está viva. Se responder não, o Kubernetes mata e recria o pod.
    \item \textbf{Readiness Probe:} Pergunta: \textit{``Você já está pronto para receber tráfego de clientes?''}.
\end{itemize}
Nosso manifesto verificava a rota \texttt{/readiness\_check}, mas dentro do código Python ela tentava fazer \texttt{db.session.query(Token).count()} sem a classe \texttt{Token} existir, devolvendo erro 500. Como o pod novo nunca dizia ``estou pronto'', o Kubernetes recusava-se a desligar o pod antigo para evitar que os usuários ficassem sem sistema! Corrigimos o sensor para apontar para a rota funcional \texttt{/health\_check}, e o pod imediatamente assumiu o status \textbf{1/1 Ready}.

\subsection{Etapa 7: O Gran Finale -- Relatórios de Negócio Respondendo 100\%}
\textbf{O que aconteceu:} Abrimos o túnel na porta 5153 e executamos as consultas HTTP. Encontramos um último detalhe na rota \texttt{/api/reports/daily\_usage} (onde estava escrito \texttt{jsonify(get\_daily\_visits)} sem os parênteses da função, gerando erro 500). Corrigido para \texttt{jsonify(get\_daily\_visits())}, as duas rotas responderam instantaneamente:
\begin{lstlisting}[language=json]
{"2023-02-07":40,"2023-02-08":202,"2023-02-09":179,"2023-02-10":158,...}
\end{lstlisting}
O microsserviço consultou os 500 registros de check-ins no PostgreSQL e entregou a agregação em JSON puro para consumo dos analistas!

\section{Decisões de Engenharia e Boas Práticas (Standout Topics)}

\begin{tcolorbox}[colback=white,colframe=tipcolor,title=\textbf{1. Por que definir Requests e Limits de CPU e Memória?},fonttitle=\bfseries]
Em análise de dados, um script mal dimensionado pode tentar carregar um dataset de 10 GB na memória e travar o computador inteiro. No Kubernetes evitamos isso com:
\begin{itemize}
    \item \textbf{Requests (\texttt{cpu: 100m, memory: 64Mi}):} É o ``bilhete mínimo'' que o pod precisa para entrar no ônibus (servidor). Garante que a aplicação sempre tenha recursos reservados.
    \item \textbf{Limits (\texttt{cpu: 250m, memory: 256Mi}):} É o ``teto de gastos''. Se o contêiner tentar usar mais de 256 MB de RAM, o Kubernetes o freia antes que ele prejudique os outros pods da máquina.
\end{itemize}
\end{tcolorbox}

\begin{tcolorbox}[colback=white,colframe=awsnavy,title=\textbf{2. Escolha da Instância EC2: Por que a família Graviton (t4g)?},fonttitle=\bfseries]
Recomendamos instâncias do tipo \textbf{\texttt{t4g.small}}. Elas utilizam os processadores \textbf{AWS Graviton2}, desenhados pela própria Amazon com arquitetura ARM (semelhante aos chips de celulares modernos e Macs Apple Silicon). Elas entregam cerca de \textbf{40\% mais velocidade} consumindo menos energia e com um \textbf{custo 20\% menor} que instâncias convencionais Intel/AMD.
\end{tcolorbox}

\begin{tcolorbox}[colback=white,colframe=succgreen,title=\textbf{3. Como Economizar Dinheiro Real na AWS?},fonttitle=\bfseries]
\begin{enumerate}
    \item \textbf{Instâncias Spot:} A AWS leiloa servidores ociosos com descontos de até 90\%. Para ambientes de homologação ou tarefas batch de dados, usar instâncias Spot com a ferramenta \textit{Karpenter} reduz drasticamente a fatura no fim do mês.
    \item \textbf{Autoescalabilidade Inteligente (HPA):} Durante o horário comercial a empresa tem muitos analistas gerando relatórios (o Kubernetes sobe 5 réplicas do pod). À noite, ele reduz para apenas 1 pod, economizando infraestrutura.
\end{enumerate}
\end{tcolorbox}
