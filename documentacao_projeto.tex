Quando vemos um diagrama de arquitetura de nuvem pela primeira vez, ele pode parecer uma coleção de caixas isoladas com nomes misteriosos: Docker, CodeBuild, ECR, EKS, Pods, Services. 

O segredo para dominar DevOps e entender a infraestrutura moderna é responder a uma pergunta simples: \textbf{``Como o componente A conversa com o componente B?''}. Quem autentica quem? Qual porta é utilizada? Como um contêiner encontra um banco de dados sem saber o IP fixo dele?

Este documento expande nossa jornada técnica anterior, detalhando a \textbf{fiação invisível} que conecta cada ferramenta da AWS e cada recurso do Kubernetes, acompanhado de fluxogramas com legendas detalhadas de funções e protocolos.
\end{tcolorbox}

\section{O Mapa Mental dos Conceitos (Analogias do Mundo Real)}

Para quem vem do ecossistema de dados (Python, SQL, Pandas), veja a correspondência direta de cada tecnologia:

\begin{itemize}[leftmargin=*]
    \item \textbf{Docker (A Marmita Lacrada):} É um ambiente virtual auto-suficiente. Ele carrega seu código Python, suas bibliotecas e o sistema operacional mínimo para garantir que o script rode idêntico em qualquer servidor do planeta, eliminando o clássico ``na minha máquina funciona''.
    \item \textbf{AWS ECR (O Almoxarifado de Imagens):} Repositório privado da AWS onde as imagens Docker empacotadas são guardadas com tags de versão (\texttt{1.0.0}, \texttt{latest}).
    \item \textbf{AWS CodeBuild (A Linha de Montagem / CI):} Servidor descartável na nuvem que, a cada novo código no GitHub, compila a imagem Docker e a envia ao ECR sem que você precise gastar a CPU do seu computador pessoal.
    \item \textbf{Kubernetes / EKS (O Maestro da Orquestra):} Gerencia os servidores e contêineres. Se o pod da aplicação cair por consumo excessivo de memória, o Kubernetes o recria imediatamente sem indisponibilidade para os usuários.
    \item \textbf{Helm (O Pip da Infraestrutura):} Em vez de escrever centenas de linhas de configuração manual para instalar um banco PostgreSQL, o Helm instala tudo com uma única instrução pronta da comunidade.
\end{itemize}

\section{Como os Componentes se Conectam: O Fio Condutor da Arquitetura}

Para entender profundamente como a infraestrutura opera, vamos analisar a conexão entre cada par de peças:

\subsection{1. Como o Desenvolvedor se conecta ao Cluster EKS}
\begin{itemize}[leftmargin=*]
    \item \textbf{O Elo de Ligação:} O arquivo local de configuração \texttt{\textasciitilde/.kube/config}.
    \item \textbf{Como funciona:} Quando você digita \texttt{kubectl get pods}, o binário do \texttt{kubectl} não conversa magicamente com o servidor. Ele lê o arquivo de configuração, descobre a URL do \textit{API Server} na AWS e executa em segundo plano o comando \texttt{aws eks get-token}. Esse token é assinado pelo serviço de identidade da AWS (STS) com base no seu usuário IAM. O Kubernetes valida a assinatura do token e permite a visualização dos recursos.
\end{itemize}

\subsection{2. Como o CodeBuild se conecta ao Registro de Imagens (ECR)}
\begin{itemize}[leftmargin=*]
    \item \textbf{O Elo de Ligação:} Chaves do IAM e o comando \texttt{docker login}.
    \item \textbf{Como funciona:} Dentro do arquivo \texttt{buildspec.yml}, executamos:
    \begin{lstlisting}
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 467369438218.dkr.ecr.us-east-1.amazonaws.com
    \end{lstlisting}
    A máquina virtual do CodeBuild utiliza sua \textit{IAM Service Role} para solicitar à AWS uma senha temporária criptografada de acesso ao ECR. Com essa credencial, o comando \texttt{docker push} ganha autorização para gravar a imagem \texttt{coworking-analytics:1.0.0}.
\end{itemize}

\subsection{3. Como a Aplicação Python encontra o Banco sem saber o IP (Service Discovery)}
\begin{itemize}[leftmargin=*]
    \item \textbf{O Elo de Ligação:} O sistema de DNS embutido do Kubernetes (\textbf{CoreDNS}).
    \item \textbf{Como funciona:} No mundo dos contêineres, os pods morrem e nascem o tempo todo, ganhando IPs dinâmicos diferentes a cada reinício. Como o script Python se conecta a um banco cujo IP muda?
    
    A resposta é o objeto \textbf{Service}. Criamos um serviço com o nome exato \texttt{postgresql}. O Kubernetes atribui a esse serviço um nome de domínio interno: \texttt{postgresql.default.svc.cluster.local}. No nosso \texttt{ConfigMap}, declaramos a variável de ambiente:
    \begin{lstlisting}
DB_HOST: "postgresql"
    \end{lstlisting}
    Quando o driver \texttt{psycopg2} do Python tenta conectar em \texttt{postgresql:5432}, o Kubernetes intercepta a requisição e a encaminha automaticamente para o pod do banco de dados correto.
\end{itemize}

\subsection{4. Como os Segredos (Senhas) chegam de forma segura ao Python}
\begin{itemize}[leftmargin=*]
    \item \textbf{O Elo de Ligação:} Os objetos \textbf{ConfigMap} e \textbf{Secret}.
    \item \textbf{Como funciona:} Dados não-sensíveis (como nome do banco e porta) foram configurados no \texttt{ConfigMap}. Já a senha do PostgreSQL foi armazenada em um \texttt{Secret} protegido. No arquivo \texttt{deployment.yaml}, usamos a instrução \texttt{secretKeyRef} para ligar a chave do secret diretamente a uma variável de ambiente chamada \texttt{DB\_PASSWORD}. O Python simplesmente lê \texttt{os.environ["DB\_PASSWORD"]}, sem nunca salvar a senha em arquivos de texto ou código-fonte.
\end{itemize}

\section{A Crônica Detalhada das Etapas (O Que Fizemos e Por Quê)}

A seguir, a narrativa completa de cada etapa executada no projeto:

\subsection{Etapa 1: O Ponto de Partida e o Mistério da AWS sem Chaves}
\textbf{O desafio:} Ao rodar \texttt{aws sts get-caller-identity} no terminal local, recebemos o erro informando que o comando não existia. Após instalá-lo, surgiu a mensagem \textit{``Unable to locate credentials''}.\\
\textbf{A explicação:} O comando \textbf{AWS CLI} é apenas o canal de comunicação com os datacenters da AWS. Mas antes de qualquer ação, a AWS exige comprovação de identidade. As variáveis exportadas no terminal (\texttt{AWS\_ACCESS\_KEY\_ID}, \texttt{AWS\_SECRET\_ACCESS\_KEY} e \texttt{AWS\_SESSION\_TOKEN}) agem como um crachá de segurança com foto e chave magnética. Com elas ativas, a AWS respondeu imediatamente reconhecendo a nossa conta.

\subsection{Etapa 2: Erguendo a Cidade do Kubernetes com \texttt{eksctl}}
\textbf{O desafio:} Executamos o comando de criação do cluster:
\begin{lstlisting}
eksctl create cluster --name my-cluster --region us-east-1 --nodegroup-name my-nodes --node-type t3.small --nodes 1
\end{lstlisting}
O comando executou por 18 minutos ininterruptos.\\
\textbf{A explicação:} Ele não estava travado; estava provisionando uma infraestrutura completa do zero por meio de automação do CloudFormation:
\begin{enumerate}
    \item Criou a \textbf{VPC}: uma rede privada e segura no datacenter da AWS em Virgínia.
    \item Criou sub-redes e tabelas de roteamento com firewalls gerenciados.
    \item Inicializou os servidores mestres de alta disponibilidade (\textbf{Control Plane}).
    \item Subiu uma instância virtual EC2 (\texttt{t3.small}) como nó operário (\textit{worker node}).
\end{enumerate}
Ao término, o \texttt{eksctl} gerou a chave \texttt{\textasciitilde/.kube/config}, habilitando o comando \texttt{kubectl} a gerenciar o cluster a partir do terminal.

\subsection{Etapa 3: Criando e Populando o Banco de Dados com Helm}
\textbf{O desafio:} Instalamos o PostgreSQL via \texttt{helm install postgresql bitnami/postgresql} e populamos o banco com os scripts SQL de tabelas, usuários e tokens.\\
\textbf{A explicação:} O \textbf{Helm} aplicou uma receita pronta de banco de dados, configurando o armazenamento e criando uma senha aleatória no \texttt{Secret}. Quando tentamos conectar via porta local \texttt{5432}, ocorreu falha de autenticação porque o computador já possuía outro PostgreSQL rodando localmente na mesma porta. Resolvemos isso injetando os scripts SQL diretamente para dentro do pod do banco na nuvem com o comando \texttt{kubectl exec}, eliminando qualquer interferência da máquina local.

\subsection{Etapa 4: Empacotando o Python no Docker e o Bug Oculto do Flask}
\textbf{O desafio:} Criamos o \texttt{Dockerfile} com \texttt{python:3.10-slim}. Nos testes dentro do pod, a aplicação quebrou com o erro:
\begin{lstlisting}
ImportError: cannot import name 'url_quote' from 'werkzeug.urls'
\end{lstlisting}
\textbf{A explicação:} O arquivo \texttt{requirements.txt} pedia apenas \texttt{flask==2.2.2}. Sem versão fixada para a biblioteca dependente \texttt{Werkzeug}, o pip instalou a versão mais recente (\texttt{Werkzeug 3.0}), que removeu a função \texttt{url\_quote} que o Flask esperava. Fixamos a dependência em \texttt{Werkzeug==2.2.2}, garantindo estabilidade e reprodutibilidade da imagem Docker.

\subsection{Etapa 5: Automatizando a Nuvem com GitHub e AWS CodeBuild}
\textbf{O desafio:} Criamos o arquivo de pipeline \texttt{buildspec.yml} e o vinculamos ao \textbf{AWS CodeBuild}.\\
\textbf{A explicação:} O CodeBuild é o robô de fábrica da AWS. A cada execução, ele sobe uma máquina efêmera, autentica no ECR, compila o \texttt{Dockerfile}, tagueia a imagem com versionamento semântico (\texttt{1.0.0} e \texttt{latest}) e a envia ao armazém \textbf{AWS ECR}, deixando-a pronta para ser consumida pelo Kubernetes.

\subsection{Etapa 6: O Mistério do Pod que Não Ficava Pronto (Readiness Probe)}
\textbf{O desafio:} O comando \texttt{kubectl rollout status} permaneceu bloqueado com a mensagem \textit{``1 old replicas are pending termination...''}, enquanto o novo pod ficava em \texttt{0/1 Running}.\\
\textbf{A explicação:} O Kubernetes possui sensores médicos chamados \textbf{Probes}. O \textbf{Readiness Probe} pergunta continuamente: \textit{``Você já está pronto para receber requisições de clientes?''}. Nosso manifesto original testava a rota \texttt{/readiness\_check}, que continha um erro de código Python ao tentar buscar um modelo \texttt{Token} inexistente, devolvendo status HTTP 500. Como o novo pod nunca dizia estar pronto, o Kubernetes recusava-se a desligar a réplica antiga para proteger os usuários. Ajustamos o probe para a rota saudável \texttt{/health\_check}, e o pod alcançou o status \textbf{1/1 Ready} instantaneamente.

\subsection{Etapa 7: O Gran Finale -- Relatórios de Negócio Respondendo 100\%}
\textbf{O desafio:} Abrimos a porta 5153 e disparamos requisições de teste. Após adicionar parênteses em \texttt{get\_daily\_visits()} no \texttt{app.py}, ambas as rotas retornaram dados completos:
\begin{lstlisting}[language=json]
{"2023-02-07":40,"2023-02-08":202,"2023-02-09":179,"2023-02-10":158,...}
\end{lstlisting}
O microsserviço consultou com sucesso os 500 usuários e tokens no PostgreSQL e entregou os relatórios analíticos em JSON formatado!

\section{Decisões de Engenharia e Boas Práticas (Standout Topics)}

\begin{tcolorbox}[colback=white,colframe=tipcolor,title=\textbf{1. Por que definir Requests e Limits de CPU e Memória?},fonttitle=\bfseries]
Em análise de dados, uma consulta pesada sem filtro pode consumir toda a memória RAM e travar o servidor inteiro. No Kubernetes prevenimos isso com:
\begin{itemize}
    \item \textbf{Requests (\texttt{cpu: 100m, memory: 64Mi}):} É a reserva garantida mínima para o pod funcionar.
    \item \textbf{Limits (\texttt{cpu: 250m, memory: 256Mi}):} É o teto máximo. Se o pod tentar usar mais de 256 MB de RAM, o Kubernetes impede o vazamento de memória antes que ele afete os outros contêineres do nó.
\end{itemize}
\end{tcolorbox}

\begin{tcolorbox}[colback=white,colframe=awsnavy,title=\textbf{2. Escolha da Instância EC2: Por que a família Graviton (t4g)?},fonttitle=\bfseries]
Recomendamos a instância \textbf{\texttt{t4g.small}}. Equipada com os processadores proprietários \textbf{AWS Graviton2} (arquitetura ARM64), ela entrega até \textbf{40\% mais performance} computacional com um \textbf{custo 20\% menor} em relação às instâncias x86 tradicionais, sendo perfeita para APIs web leves e relatórios analíticos.
\end{tcolorbox}

\begin{tcolorbox}[colback=white,colframe=succgreen,title=\textbf{3. Como Economizar Dinheiro Real na AWS?},fonttitle=\bfseries]
\begin{enumerate}
    \item \textbf{Instâncias Spot com Karpenter:} A AWS oferece servidores ociosos com até 90\% de desconto. Para tarefas analíticas e ambientes de teste, usar instâncias Spot reduz dramaticamente os custos.
    \item \textbf{Autoescalabilidade (HPA):} Permite que o cluster aumente o número de réplicas durante o pico de uso comercial e encolha para apenas 1 pod nos finais de semana e noites.
\end{enumerate}
\end{tcolorbox}
